# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Forever** is two World of Warcraft addons for the **WoW Forever** client (interface 16001, a Midnight/Mainline client with some `Camelot` Blizzard addons). There is no build step: each top-level addon folder _is_ an addon, loaded by the game in its `.toc` order, and `scripts/link.sh "<game>/Interface/AddOns"` symlinks them into the game. README.md is the authoritative guide (each addon's modules, the `ns:NewModule` API, option fields, the "keep the addon light" rules); read it before adding or changing a module.

**Names (3.3.0):** Forever Gearbox was previously called Forever Tweaks, and Forever Codex was previously called Forever Compendium. Each Part.lua's `formerSaved`/`formerCharSaved` takes the old saved variables over once (`Store.Init`), and `Core/Plugin.lua`'s `TakeOver` reads a module's settings from Forever++'s profile under `ForeverGearbox<Name>` or `ForeverTweaks<Name>` (migration 20). Some old names stay on purpose, never "fix" them: `ForeverTweaksAPI` (alias of `ForeverGearboxAPI`), the Update Notice's addon channel `"ForeverTweaks"`, Baganator widget ids `ForeverTweaks_*` (Baganator saves corners by id), the key binding `FOREVERCOMPENDIUM_TOGGLE` (the game saves keys by name), Codex's export header `FC1:` and sharing prefix `FCompendium`, and older Changelog entries and migrations.

- **Shared/**: the runtime both addons carry (events, modules, saved variables, options, slash commands, bindings, Kit/KitRows/Windows/Popups/EditMode/Widgets/Controls). Edit only the root `Shared/`, then `scripts/sync-shared.sh` copies it into `ForeverGearbox/Shared/` and `ForeverCodex/Shared/` (the `lint` scenario and CI fail on a stale copy; desloppify excludes the copies). There is no ForeverCore any more (removed in 3.0.0).
- **ForeverGearbox/**: quality-of-life modules (`/fg`), `ForeverGearboxAPI` (and `ForeverTweaksAPI`, the same table under its 3.2 name). **An addon of its own** (3.3.0, the user's call): settings in `ForeverGearboxDB`, its modules started by itself (`Init.lua`: `ns:Start`, `RegisterSettings`), its own entry in Settings > AddOns drawn exactly as Forever++'s Modules page (`Settings/Alone.lua`, `Settings/AlonePage.lua`, rows from `UI/ForeverRows.lua`; `/fg`; a module's `BuildPage` inline under its options; Advanced Graphics a subpage under it while on, `VisualsPage.UseHost`), never a window of its own: Gearbox doesn't load the shared settings window (`Shared/Settings/`, Codex's only: `sync-shared.sh` leaves it out of `ForeverGearbox/Shared/`, CI diffs with `-x Settings`). Forever++ is optional (`## OptionalDeps: ForeverPlusPlus`) and touched only while **Forever++ Integration** is on (module key `ForeverPlusPlus`, `Modules/Addons/ForeverPlusPlus.lua`, category addons, offered while Forever++ is loaded, off by default; `ns.Plugin.Integrated()`; others follow it through `ns:OnChanged(_, "ForeverPlusPlus", "enabled")`): Upgrade Arrows in Baganator judges by Forever++'s Upgrade Arrows (`GetItemUpgradeInfo`, `UPGRADES_UPDATED`) instead of its own (`Lib/ItemStats.lua`, `Lib/Equipment.lua`, `Lib/Upgrades.lua`, from Forever++'s); modules with `attach = "<Forever++ module>"` (Quest Markers → QuestNameplates, Fishing → FishingCast, Upgrade Arrows in Baganator → UpgradeArrows) are also a "Forever Gearbox" section on that module's page (`Core/Attach.lua`, `UI/ForeverPage.lua`: found through Blizzard's `Settings.RegisterCanvasLayoutCategory`, hooked; no Forever++ file is touched; Forever++'s pages are stacks with `entries` like `Kit.NewStack`) but always modules of their own; Quest Markers hides Forever++'s own nameplate mark; Advanced Graphics is listed under Forever++ too; a console variable notice gets a Find button (`/fpp cvar`); `OtherAddons`' Forever++ calls answer nil while it's off. Nothing is registered on Forever++'s Modules page any more. Gearbox complements Forever++ (the user's call, 3.3.0): a feature may overlap one of Forever++'s, and a player with both turns one off; no notice about it. The modules removed in 3.0.0 for being Forever++'s (its chat, tooltip, class colors, gathering map, Hide Error Messages..., and Keep Messages, the Tracker's level sort, New in Forever, Object Names, Threat and Gathering Session): never reuse their names, and no module that only sets a console variable (Forever++'s Console Variables sets and locks those: Rotate Minimap is gone for that, twice). The one exception, the user's call (3.2.0, one page since 3.3.0): Advanced Graphics (module key Visuals: `Modules/Interface/Visuals.lua`, `VisualsPage.lua`, `DynamicLight.lua`, `DynamicLightPage.lua`), how the game looks on top of its graphics menu with presets and value protection; its settings in two columns (`Kit.AddColumns`), Dynamic Light under them across the page. No loot sparkles there: Forever++'s Quest Item Sparkles has them. Quest Items and Full Bags need QuestieDB (`Shared/Lib/QuestieDB.lua`, shared with Codex, as Forever++'s Quest Pins: loaded on demand, red and locked off without it; `Module:SetActive` never starts a locked module). Drawer (`Modules/Interface/Drawer.lua`, `DrawerFlyout.lua`, `DrawerEditor.lua`): Plumber's Drawer Macro idea in our own code (Plumber has no license); `MacroDrawer` was a 1.6.0 module: never reuse that name. Removed in 3.3.0 (the user's call; migrations 17-19), never re-add them or reuse their names: the Forever++ ports Hide Chat Buttons (`HideChatButtons`; `ChatButtons` is our own since), Map Pan & Zoom, Melee Range, Keep Windows Open, the Tracker and Dialogue Keys.
- **ForeverCodex/**: needs Forever Gearbox (`## Dependencies: ForeverGearbox`, so Forever++ too; `## OptionalDeps: QuestieDB, Spoken, Spoken_Quests, OpenMap, Questie`; with OpenMap its `Modules/Map/OpenMap.lua` works as Questie does with it, through `OpenMapAPI`: QuestieDB as its townsfolk provider while Questie isn't loaded, its menu switches, dungeon cards; `UI/MapPins.lua` draws every zone in OpenMap's stitched view); its settings window (`Shared/Settings/`, in the journal's look through `SettingsWindow.SetLook` in `Init.lua`), the minimap button and Update Notice (`Modules/Settings/`), `UI/List|MapPins|Bags.lua`, and both addons' release notes (`Changelog.lua`). The creature/NPC/loot/quest journal (`/codex`): its book (creatures, NPCs, items) learned only from what the player sees; no Quests tab (Spoken's Azeroth's Compendium lists quests): a quest named in the journal opens through `ns.ShowQuest` in Blizzard's quest log while it's in your log, else Spoken's compendium when it has the quest's words (`Lib/Spoken.lua`), else the journal's quest window (`Modules/Journal/QuestPage.lua`), which shows only discovered quests (`Lib/QuestIndex.lua`: the book's, the log's, the game's completed ones; never give one away); it, the journal's links and Quest Pins' "quests you can take" (`Lib/QuestGivers.lua`, Forever++'s rules, stepping back while Forever++'s Quest Pins is on) may read QuestieDB, never write it into the book. It does what Forever Bestiary (Arxie's addon, unlicensed: never copy its code) did: a journal in the look of the game's own books as Spoken's Azeroth's Compendium has it (no Spoken code: it has no license; ## WoW API skills (wow-addon-dev plugin)

`.claude/settings.json` enables the `wow-addon-dev` plugin (WoW Addon API Agents, marketplace `JBurlison/WoWAddonAPIAgents`). Use it on every addon task, always targeting **Forever** (interface 16001; never Retail or Classic):

- Before writing or changing code that calls a game API, event, widget method or Blizzard frame, look it up with the plugin's skills: `wow-client-targets` (Forever), then `wow-api-index` and the domain skill it routes to (e.g. `wow-api-quests`, `wow-api-map-navigation`, `wow-api-items-inventory`, `wow-api-events`, `wow-api-lua-environment` for taint/secret values, `wow-api-widget`, `wow-api-framexml`). For UI: `wow-native-ui`, `wow-ui-skinning` and `wow-controller-support`.
- `docs/forever-api.md` still wins: it records what was confirmed in game. The plugin's catalogs are source declarations from the `forever` branch, not proof that something works in game. Something confirmed there but missing from `docs/forever-api.md` gets added to it with the plugin as its source and marked "source-declared". Test it in game before relying on it.
- `.claude/hooks/skill-activation.py` (a `UserPromptSubmit` hook in `.claude/settings.json`) matches each prompt against `.claude/hooks/skill-rules.json` and names the skills to load first; it is silent when nothing matches. A new skill or a new Forever domain gets a rule there (names exactly as the Skill tool lists them).
- The repo's own rules come first: its structure, Shared runtime, tests, locales, release steps and Forever++ companion rules. When the plugin's generic workflow (`wow-addon-development`: requirement matrices, options menus, localization, Witchcraft/UIForever testing) conflicts with this file or README.md, follow this file and README.md.

## Commands

```sh
lua5.1 tests/run.lua              # all scenarios, each in a fresh Lua process
lua5.1 tests/run.lua suite        # one scenario (names: tests/run.lua GROUPS)
find . -name '*.lua' -not -path './.git/*' -print0 | xargs -0 luac5.1 -p   # syntax
grep -rnP '[^\x00-\x7F]' --include='*.lua' --include='*.toc' .            # must print nothing: ASCII only
desloppify scan --path .                                                  # CI fails below objective 100
```

CI (`.github/workflows/check.yml`) also checks that each addon's TOC lists every one of its `.lua` files (and every listed file exists), that each addon's `Shared/` equals the root's, and that both TOCs share one `## Version`. After editing `Shared/`, run `scripts/sync-shared.sh`. In-game, a new file needs a full game restart; edits only need `/reload`.

## Architecture

- **One namespace per addon.** Each addon's TOC lists the runtime first (`Shared\Core\Core.lua` → `Members.lua` → `Module.lua` → `Locales\enUS_Core.lua` → Store, Options, Profiler, DebugReport, Slash, Commands, Bindings → `Shared\UI\` Kit, KitRows, Windows, Popups, EditMode, Widgets, Controls), then its `Part.lua` (`ns:NewMember(name, ns, info)`: the addon's one member, `ns.member`), `Locales/`, `Migrations.lua`, `Lib/`, `UI/`, modules, and `Init.lua` last. Codex also loads `Settings/` before its modules. The only globals are `ForeverGearboxAPI` (and its old name `ForeverTweaksAPI`), `<Addon>_RunBinding` (each `Bindings.xml`), `ForeverCodex_ToggleJournal`, the saved variables and slash commands. Shared code must not name an addon: use `ns.name`/`ns.title`.
- **Init**: Both addons' `Init.lua` run `Store.Init` on ADDON_LOADED and `ns:Start`, `RegisterSettings`, `RegisterSlash` at PLAYER_LOGIN. Gearbox' also runs `Plugin.SettleAlone` (1.x settings kept for Forever++ become its own) and, once after migration 20, `Plugin.TakeOver` (its settings from Forever++'s profile) on ADDON_LOADED.
- **All events/timers/hooks go through one shared frame per addon** (module-side wrappers in `Core/Module.lua`), owned by a module, dispatched via `securecallfunction` so one failing handler can't stop others, automatically stopped when the module disables, and timed by `Core/Profiler.lua`. Modules must not create their own event frames or raw `C_Timer`/`hooksecurefunc` calls. A hook installed by an earlier enable stays installed (inert while off): a hook body must re-check anything that makes the module stand down.
- **Saved variables (`Shared/Core/Store.lua`)**: `member.saved`/`member.charSaved` hold `settings` (sparse over `defaults`) and `data` (table defaults, never cleared by Defaults), and the addon's own top-level settings (`ns.db`: quiet, debug, window). A layout change bumps `layout` in `Part.lua` and adds `ns:Migrate(version, fn(db))` in the addon's `Migrations.lua` (Gearbox 14: 1.x settings kept aside in `movedSettings`/`enabledDefaults`, settled by `Plugin.SettleAlone`; 20: settings taken back from Forever++'s profile; Codex 3: `ForeverCoreDB` imported then cleared; 4: friendly NPCs known for something marked `npc`, ones only seen and critters dropped; 5: players' pets, guardians and totems dropped).
- **Settings UI**: the shared window (`Shared/Settings/Window.lua`, a frame per addon named `<Addon>SettingsFrame`; Codex only (Gearbox has its own entry in Forever++'s look, `Settings/Alone*.lua`); an addon's look through `SettingsWindow.SetLook`, Blizzard's insets by default) shows Settings (`General.lua` and every `category = "settings"` module), its Modules page (`ModulesPage.lua`, built from each module's `options`), About, Debug, Changelog; Settings > AddOns > the addon is a launcher. Gearbox' page and its sections on Forever++'s pages (with the integration) are drawn in Forever++'s own row layout (`UI/ForeverRows.lua`). `/fg` and its subcommands read the same option tables.
- **Categories are per addon** (`categories` in `Part.lua`; "other" and "settings" always added). Labels are `L.CATEGORY_<KEY>`.
- **Map pins** (Codex) use `ns.MapPins.Both(mod, opts)` (`ForeverCodex/UI/MapPins.lua`).
- **Key bindings**: each addon's `Bindings.xml` calls `<Addon>_RunBinding("<NAME>")`; the module registers what it does with `ns:AddBinding(owner, name, fn)` (`Shared/Core/Bindings.lua`); binding names and headers are `BINDING_*` globals in the addon's locale file.
- **Finding an item in the bags** (Codex): `ns.Bags.Has(itemID)` / `ns.Bags.Find(mod, itemID)` (`ForeverCodex/UI/Bags.lua`).
- **On-screen widgets** use `ns.Widgets.AddDisplay` (`Shared/UI/Widgets.lua`), which plugs into the game's Edit Mode via `Shared/UI/EditMode.lua`.
- **`ForeverGearbox/API.lua`** exposes `ForeverGearboxAPI.v1` (also as `ForeverTweaksAPI.v1`, its name before 3.3.0: keep it): read-only, returns copies, swallows errors to nil, and is append-only (never rename/remove). It covers Gearbox' modules only.
- **Blizzard frames we wrap** (deliberate, see docs/code-health.md): none since Map Pan & Zoom went (3.3.0). Blizzard's objective tracker is never touched (the Tracker went in 3.3.0; under Midnight's secret values addon code in its update taints all of it).

## Conventions

- Every player-facing string lives in a `Locales/` file as `L.KEY`: the runtime's in `Shared/Locales/enUS_Core.lua`, each addon's in its own (`enUS.lua` for categories and pages, `enUS_Modules.lua` per module, Gearbox' `enUS_Shared.lua` for the modules WilduTools/Plumber also have, `enUS_Interface.lua` (Cooldown Layout, Advanced Graphics) and `enUS_Quests.lua` (Quest Markers)); tests fail on any missing string. Gearbox' text is written in Forever++'s voice (a module's description and an option's tooltip say what to do: "Show...", "Mark...", never "Shows..."), as Forever++'s own.
- **Secure buttons** (only Drawer's: `Modules/Interface/DrawerFlyout.lua`, its root, strip, action buttons and one `SecureHandlerClickTemplate` handler per drawer macro, opened by `/click` and a restricted `_onclick` snippet; `tests/stubs/macros.lua`'s `W.RunSecure` runs a snippet as the game does) are set up, shown, hidden and moved only out of combat (`ns:AfterCombat`, or hide on `PLAYER_REGEN_DISABLED`); anything that must happen in combat is a restricted snippet. Don't anchor a protected frame to one of our ordinary frames. The test stand-in fails a run that touches a protected frame in combat.
- **Only use APIs that exist in Forever.** `docs/forever-api.md` lists what's confirmed present (and absent, e.g. `MouseIsOver`, `C_Console`) with sources; check there first, add anything newly verified, and don't write fallbacks for things Forever has. Its "Other references" section lists Wowpedia, Townlong-yak and the texture repo; those describe retail, so confirm against the `forever` sources. Under the test harness's strict mode, reading any global the stub (`tests/wow.lua`, `tests/stubs/`) doesn't define is a failure: add a stand-in (or a `W.OPTIONAL` entry if the addon intentionally probes for it), and new events to `W.EVENTS`. Forever++ is `tests/stubs/foreverplusplus.lua`, loaded for Gearbox unless a test sets `W.withoutForeverPlusPlus` (`W.FPP.own` its own modules (those Gearbox goes with are there, on), `W.FPP.SetOwn` toggles one, `W.FPP.upgrades` Upgrade Arrows' answers; a Gearbox module is toggled with `ns:SetEnabled`, Forever++ Integration with `ns:SetEnabled("ForeverPlusPlus", true)`), on-demand addons `W.addonInfo` (QuestieDB installed, loaded on demand), the world map's scroll container `tests/stubs/worldmap.lua`, macros, cooldowns, mounts and restricted snippets `tests/stubs/macros.lua` (`W.macros`, `W.RunSecure(frame, "_onclick")`).
- **Codex's book** comes only from what the player sees (no Questie/Bestiary code; QuestieDB only through `Shared/Lib/QuestieDB.lua` for the Quests page and links, never stored); the Recorder meets a creature only if `UnitCanAttack` (or when you loot its corpse: loot of one not met yet waits in `RecorderLoot.lua` until it is; loot is read on `LOOT_READY`), never another player's pet, guardian or totem (`UnitIsOtherPlayersPet`, the tooltip's `UnitOwner` line, `Book.LooksOwned` for old records, imports and shares), a friendly NPC only on an interaction (gossip, quest, merchant, trainer, taxi, bank), never vehicles, critters, battle pets or from a flight path; everything learned goes through `ForeverCodex/Lib/Book.lua`, and every game value passes `ns.Plain` (drops Midnight's secret values) before it's stored or compared. Never in chat, never touch Blizzard's quest tracker; sounds only through `ns.Sound` (`Lib/Sound.lua`), which the Journal's Sounds option turns off.
- Every release: bump `## Version` in **both** `.toc` files (one version) and add a newest-first entry to `ForeverCodex/Changelog.lua` (both addons' notes). New modules/options set `added = "<version>"` to get a NEW badge.
- Code adapted from Forever++ (MIT, see `LICENSE-ForeverPlusPlus.txt`), and OpenMap (MIT) — keep the credits in README and file headers. OpenMap_Tweaks has no license: copy nothing from it.

## Code health

`docs/code-health.md` has the suite's rules ("The suite") and those from two desloppify review rounds, plus the decisions that are deliberate (don't "fix" those). The ones most often broken:

- Use the shared helpers instead of hand-rolling them: `M:Soon(fn)` (redo once next frame), `M:IsPending`/`M:CancelTimer` (tickers), `M:HookCallback` (tooltip post calls, callback registries), `ns.ChargedCall` (call into a module without passing the owner), `BagButtons.RegisterWidget` (Baganator), `ns.QuestLog.Listen`, `ns:Announce` (news for `API.lua`), `M:OnNews`/`M:OnChanged` (a module hearing news or setting changes, only while on), `ns.Plain` (the only secret-value check: `issecretvalue` stays in `Shared/Core/Core.lua`), `ns.MoneyText` (all money text). The `lint` scenario checks for unused header locals, `L` keys defined twice and stray `issecretvalue`. No `hooked`/`registered` flags, no probing `M.timers`.
- What an option value means lives only in `Shared/Core/Options.lua` (`Parse`, `ParseNumber`, `ValueText`, `SliderText`, `Fits`, `Requires`).
- Don't `pcall` or nil-check APIs `docs/forever-api.md` lists as present; `pcall` only other addons' APIs and log their errors.
- Split big files by responsibility, not by trimming; update README/CLAUDE.md/file headers in the same change as a move.
- New test scenarios go in `GROUPS` in `tests/run.lua`; use `W.Advance` for delays; a bug fix gets a test that fails without it. In a test, each addon's `ns` is what `W.LoadAddon` returns; there is no shared core namespace.

desloppify (`pip install "desloppify[full]==1.0"`, Python 3.11+): `desloppify scan --path .` then follow `desloppify next`; the agent workflow is in `.claude/skills/desloppify/SKILL.md`. The subjective review (`desloppify review`) launches about 20 reviewer agents, so run it after a large batch of changes, not every change.
